# نقشه راه Hokm Club

این سند برنامه مرحله‌ای توسعه ربات تلگرام و Telegram Mini App بازی حکم ایرانی است. هدف این است که هر فاز به بخش‌های کوچک، قابل تست و قابل تأیید تقسیم شود و بعد از تأیید، وارد بخش بعدی شویم.

## وضعیت فعلی

### فاز ۱ — MVP قابل اجرا و تست اولیه — انجام شده

خروجی‌های فعلی:

- ربات تلگرام فعال با دستورات `/start` و `/newgame`
- Mini App قابل باز شدن داخل تلگرام
- بک‌اند Node/Express/Socket.IO روی لپتاپ
- تونل رایگان Pinggy/Cloudflare برای HTTPS موقت
- موتور قوانین پایه حکم
- ساخت میز و ورود بازیکن
- تست تک‌نفره با ربات‌های ساده
- اجرای محلی بدون دامنه و بدون Vercel

فاز ۱ عمداً MVP است؛ یعنی ظاهر، پایداری state، reconnect و امنیت Telegram auth هنوز کامل نیستند.

# فاز ۲ — پایدارسازی فنی

هدف فاز ۲ این است که بازی از حالت «دموی حافظه‌ای» به حالت قابل اتکاتر برسد؛ یعنی state، room، user و reconnect قابل مدیریت شوند.

## فاز ۲.۱ — لایه ذخیره‌سازی محلی

هدف:

- اضافه کردن دیتابیس/ذخیره‌سازی محلی سبک
- ذخیره roomها و game state
- جلوگیری از پاک شدن کامل میزها با restart بک‌اند
- آماده‌سازی معماری برای session و reconnect

خروجی مورد انتظار:

- بک‌اند هنگام شروع، roomهای ذخیره‌شده را load کند.
- هر تغییر مهم room/game ذخیره شود.
- فایل دیتابیس/داده محلی commit نشود.
- تست ذخیره و بازیابی وجود داشته باشد.

## فاز ۲.۲ — Session و Reconnect

هدف:

- بازیکن بعد از بستن Mini App بتواند به همان میز و صندلی برگردد.
- وضعیت آنلاین/آفلاین مدیریت شود.
- socket reconnect تجربه قابل قبولی داشته باشد.

کارها:

- تعریف session پایدار برای هر player
- ذخیره session در localStorage و backend
- reconnect خودکار socket
- نمایش وضعیت connected/disconnected در UI
- جلوگیری از گرفتن صندلی تکراری توسط همان کاربر

## فاز ۲.۳ — احراز هویت Telegram Mini App

هدف:

- اطمینان از اینکه کاربر واقعاً همان Telegram user است.
- جلوگیری از جعل userId/playerId در کلاینت.

کارها:

- verify کردن initData با Bot Token
- ساخت/به‌روزرسانی user واقعی تلگرام
- اتصال room player به Telegram user تأییدشده

## فاز ۲.۴ — چرخه عمر Room

کارها:

- جلوگیری از start غیرمجاز

- محدودیت تعداد میزها برای جلوگیری از اسپم

## فاز ۲.۵ — تست، مستندات و hardening

هدف:

- اطمینان از اینکه فاز ۲ قابل اتکا است.

کارها:

- تست‌های room lifecycle
- تست reconnect
- آپدیت README و راهنمای اجرای لپتاپی
- بررسی خطاها و edge caseها

# فاز ۲.۶ — ماژولار کردن پروژه (Refactor) ✅ انجام شد

این فاز **بین فاز ۲ و فاز ۳** انجام می‌شود و هیچ قابلیت جدیدی به بازی اضافه نمی‌کند.
هدفش فقط تمیز کردن ساختار کد است، قبل از اینکه فاز ۳ و ۴ حجم زیادی کد جدید اضافه کنند.

## چرا این فاز لازم است

در پایان فاز ۲، فایل `apps/api/src/server.ts` به حدود **۸۷۰ خط** رسیده و همه‌ی
مسئولیت‌های زیر را هم‌زمان بر عهده دارد:

- بارگذاری تنظیمات و متغیرهای محیطی
- تعریف تمام routeهای HTTP
- تمام رویدادهای Socket.IO
- منطق ساخت و مدیریت میز
- منطق هوش مصنوعی ربات‌ها
- راه‌اندازی ربات تلگرام
- زمان‌بندی پاک‌سازی میزهای قدیمی
- سرو کردن فایل‌های Mini App

فایل `apps/web/src/main.tsx` هم حدود **۷۷۰ خط** است و کل رابط کاربری، مدیریت state،
ارتباط با شبکه و همه‌ی کامپوننت‌ها را در یک فایل جا داده است.

این وضعیت چند مشکل واقعی می‌سازد:

1. **پیدا کردن کد سخت می‌شود.** برای یک تغییر کوچک باید در یک فایل بزرگ جست‌وجو کرد.
2. **ریسک تغییرات بالا می‌رود.** یک ویرایش اشتباه می‌تواند بخش نامرتبطی را خراب کند.
3. **تست کردن سخت‌تر است.** منطقی که داخل یک route تعریف شده، جز از راه HTTP قابل تست نیست.
4. **کار موازی ممکن نیست.** هر تغییری در همان یک فایل conflict می‌سازد.

نکته مهم: بخش‌هایی که در فاز ۲ به‌صورت ماژول جدا نوشته شدند
(`session.ts`، `telegram-auth.ts`، `room-lifecycle.ts`، `rate-limit.ts`، `sanitize.ts`،
`messages.ts`، `storage.ts`) دقیقاً نشان می‌دهند این کار چقدر نتیجه می‌دهد: هر کدام
مستقل و با تست واحد قابل بررسی‌اند.

## ساختار هدف برای بک‌اند

```text
apps/api/src/
  config.ts          # خواندن و اعتبارسنجی .env در یک نقطه
  state.ts           # نگهداری میزها در حافظه + persist
  types.ts           # تعریف Room و RoomPlayer
  errors.ts          # HttpError و normalizeError
  http/
    index.ts         # ساخت اپ Express و اتصال routerها
    rooms.routes.ts  # ساخت میز، join، وضعیت میز
    lobby.routes.ts  # add-bot، remove-bot، ready، leave
    middleware.ts    # rate limit، هندلر خطا، CORS
  realtime/
    socket.ts        # راه‌اندازی Socket.IO
    handlers.ts      # room:join و رویدادهای بازی
    broadcast.ts     # emitRoom و viewFor
  game/
    room-service.ts  # createRoom، joinRoom، leaveRoom، maybeStartGame
    bots.ts          # autoAdvanceBots و منطق انتخاب کارت ربات
  telegram/
    bot.ts           # دستورات ربات تلگرام
  jobs/
    cleanup.ts       # پاک‌سازی دوره‌ای میزها
  server.ts          # فقط سرهم‌بندی و اجرا (هدف: زیر ۱۰۰ خط)
```

## قوانین اجرای این فاز

1. **هیچ تغییر رفتاری مجاز نیست.** خروجی APIها، پیام‌ها و ظاهر UI باید دقیقاً یکسان بماند.
2. **تست‌ها تور ایمنی هستند.** مجموعه تست فعلی (۱۴۲ تست) قبل و بعد از هر گام باید کامل سبز باشد.
3. **گام‌های کوچک.** هر بار یک ماژول جدا شود و بلافاصله `build`، `test` و `typecheck` اجرا شود.
4. **بدون تغییر همزمان.** رفع باگ یا قابلیت جدید در همین فاز انجام نمی‌شود تا diff قابل بازبینی بماند.

# فاز ۳ — کامل‌تر کردن قوانین و تجربه بازی

هدف فاز ۳ نزدیک کردن بازی به قوانین کامل‌تر حکم ایرانی است.

## ۳.۱ — حالت‌های بازی ۴، ۳ و ۲ نفره ✅ انجام شد

تا اینجا فقط حکم چهار نفره پشتیبانی می‌شد. حالا سه حالت رسمی داریم و در هر حالت
می‌شود جای نفرات کم، ربات اضافه کرد.

### مقایسه سه حالت

| | حکم ۴ نفره (`classic4`) | حکم ۳ نفره (`solo3`) | حکم ۲ نفره (`duel2`) |
|---|---|---|---|
| تعداد صندلی | ۴ | ۳ | ۲ |
| تیم‌بندی | ۱ و ۳ مقابل ۲ و ۴ | هرکس برای خودش | هرکس برای خودش |
| کارت حذف‌شده | ندارد | یک کارت ۲ (۵۱ کارت) | ندارد |
| کارت هر نفر | ۱۳ | ۱۷ | ۱۳ |
| پخش کارت | ۵ + ۴ + ۴ | ۵ + ۴ + ۴ + ۴ | ۵ سپس سوزاندن و برداشتن |
| برد راند | ۷ دست | ۷ دست | ۷ دست |
| بازیکن واقعی | ۱ تا ۴ نفر | ۱ تا ۳ نفر | ۱ تا ۲ نفر |

### قوانین حکم سه نفره

مطابق قوانین رایج ایرانی: چون ۵۲ بر ۳ بخش‌پذیر نیست، **یک کارت ۲ از بازی خارج
می‌شود** تا ۵۱ کارت بماند و به هر نفر ۱۷ کارت برسد. پخش کارت یک دور ۵تایی
(برای انتخاب حکم) و سپس سه دور ۴تایی است.

نکته پیاده‌سازی: کارتی که حذف می‌شود **هرگز از خال حکم نیست**، چون حذف یک کارت
حکم قدرت خال حکم را تغییر می‌دهد. چون حکم بعد از پخش اولیه انتخاب می‌شود،
حذف کارت درست بعد از تعیین حکم انجام می‌گیرد.

بقیه قوانین (رعایت خال زمینه، بریدن با حکم، کوت) مثل حکم چهار نفره است، با این
تفاوت که هر بازیکن تیم مستقل خودش است.

### قوانین حکم دو نفره

این حالت بیشترین تفاوت را دارد و مرحله‌های اختصاصی خودش را دارد:

1. به هر نفر **۵ کارت** داده می‌شود.
2. حاکم **خال حکم** را انتخاب می‌کند.
3. **مرحله سوزاندن** (`discarding`): هر دو بازیکن ۲ کارت بی‌ارزش خود را
   به‌صورت پنهان از بازی خارج می‌کنند.
4. **مرحله برداشتن** (`drawing`): به نوبت از دسته وسط کارت برمی‌دارند.
   قانون کلیدی:
   - کارت رو می‌شود و فقط خودِ بازیکن آن را می‌بیند.
   - اگر **نگه دارد**، کارت بعدی نادیده سوزانده می‌شود.
   - اگر **بسوزاند**، کارت بعدی را ندیده مجبور است بردارد.
5. وقتی هرکدام به ۱۳ کارت رسیدند، بازی مثل حکم معمولی انجام می‌شود.
6. هرکس زودتر ۷ دست بگیرد برنده راند است. کوت هم اعمال می‌شود.

### پیاده‌سازی فنی

- ماژول جدید `packages/game-engine/src/modes.ts` تفاوت هر حالت را در یک
  `ModeConfig` نگه می‌دارد، پس منطق بازی به‌جای `if` های پراکنده از پیکربندی
  خوانده می‌شود.
- `TeamId` از `0 | 1` به `number` تغییر کرد تا در حالت‌های انفرادی هر صندلی
  تیم خودش باشد.
- فازهای جدید `discarding` و `drawing` به `GamePhase` اضافه شد.
- رویدادهای جدید Socket.IO: `game:discard`، `game:draw`، `game:resolve_draw`.
- `stock` (کارت‌های پخش‌نشده) هرگز به کلاینت فرستاده نمی‌شود؛ فقط `stockCount`.
  کارت رو شده هم فقط برای همان بازیکنی که برداشته ارسال می‌شود.
- ربات‌ها هر سه حالت را می‌فهمند: ضعیف‌ترین کارت‌ها را می‌سوزانند و کارت
  برداشته‌شده را نگه می‌دارند.
- میزهای ذخیره‌شده قبل از این تغییر، خودکار `classic4` در نظر گرفته می‌شوند.

### رابط کاربری

- انتخاب حالت بازی در صفحه اول (۴/۳/۲ نفره).
- دکمه **«قوانین این حالت را بلد نیستم»** که یک راهنمای کوتاه، ساده و گویا
  برای همان حالت نشان می‌دهد. همین دکمه در لابی هم هست.
- در حالت دو نفره: انتخاب کارت برای سوزاندن و کارت‌های «نگه می‌دارم / می‌سوزانم».
- جدول امتیاز در حالت‌های انفرادی به‌جای «تیم ۱ / تیم ۲» شکل «تو / حریفان» دارد.

## ۳.۲ — تنظیمات میز و قوانین اختیاری (مرحله بعدی) ⏭️

الان همه چیز ثابت است: امتیاز هدف همیشه ۷ است، کوت و حاکم‌کوت همیشه فعال‌اند و
هیچ قانون اختیاری وجود ندارد. در این مرحله سازنده میز می‌تواند قبل از شروع،
قوانین را تنظیم کند.

### ۳.۲.۱ — امتیاز هدف قابل تنظیم ✅ انجام شد

- سازنده میز بین **۳، ۵، ۷ یا ۱۱** امتیاز انتخاب می‌کند (پیش‌فرض ۷).
- انتخاب هم در صفحه اول (موقع ساخت میز) و هم در **تنظیمات میز** داخل لابی ممکن است.
- سرور فقط این چهار مقدار را می‌پذیرد؛ کلاینت نمی‌تواند عدد دلخواه بفرستد.
- endpoint جدید `POST /rooms/:id/settings` که فقط برای **سازنده میز** است و
  می‌تواند هم امتیاز هدف و هم حالت بازی را عوض کند.
- با تغییر حالت بازی، میز اندازه‌اش عوض می‌شود: ربات‌های اضافی حذف می‌شوند و
  **آمادگی همه صفر می‌شود** تا کسی ناخواسته وارد بازی با قوانین جدید نشود.
- اگر تعداد بازیکنان انسانی بیشتر از ظرفیت حالت جدید باشد، تغییر رد می‌شود
  (`TOO_MANY_PLAYERS`).
- امتیاز هدف در جدول بالای میز نمایش داده می‌شود («تا ۵ امتیاز»).

### قانون کوت (تأیید و تثبیت شد)

قوانین امتیازدهی از قبل درست پیاده شده بودند و حالا با ۱۲ تست اختصاصی قفل شدند:

| حالت | امتیاز |
|---|---|
| برد عادی | ۱ |
| **کوت** — حریف حتی یک دست هم نبرد | ۲ |
| **حاکم‌کوت** — تیم/بازیکنِ حاکم کوت شود | ۳ |

در حالت چهار نفره امتیاز به **تیم** می‌رسد و در حالت‌های دو و سه نفره به **خود
بازیکن**. در حالت سه نفره کوت یعنی *هر دو* حریف بدون دست مانده باشند.

### ۳.۲.۲ — قانون «ده‌لو کم» ✅ انجام شد

اگر ۵ کارت اولِ حاکم هیچ کارت عکس‌داری (آس، شاه، بی‌بی، سرباز) نداشته باشد،
حاکم می‌تواند بخواهد کارت‌ها دوباره پخش شوند.

- رویداد جدید `game:redeal` در مرحله `waiting_for_trump`.
- **سرور خودش شرط را بررسی می‌کند**؛ کلاینت نمی‌تواند دست ضعیف جعل کند.
- سقف ۲ بار پشت‌سرهم تا میز قفل نشود؛ بعد از آن درخواست رد می‌شود.
- پیش‌فرض **روشن** است (مثل بازی واقعی) و از تنظیمات میز خاموش می‌شود.
- حاکم فقط وقتی دکمه را می‌بیند که واقعاً شرایطش را داشته باشد.
- ربات‌ها هم وقتی حاکم باشند و دستشان ضعیف باشد از این حق استفاده می‌کنند.

### ۳.۲.۳ — قانون «بام» ✅ انجام شد

اگر کسی بعد از رسیدن به ۷ دست ادامه دهد و **همه دست‌های راند** را ببرد،
«بام» کرده و **کل بازی** همان‌جا تمام می‌شود، صرف‌نظر از امتیاز.

- وقتی روشن باشد، راند در ۷ دست متوقف نمی‌شود و ادامه پیدا می‌کند.
- **بهینه‌سازی مهم**: به‌محض اینکه حریف حتی یک دست بگیرد، بام غیرممکن می‌شود و
  راند بلافاصله تمام می‌شود. بنابراین دست‌های تصمیم‌گرفته‌شده بی‌دلیل ادامه پیدا نمی‌کنند.
- تعداد دست لازم بر اساس حالت فرق می‌کند: ۱۳ در بازی ۴ و ۲ نفره، ۱۷ در بازی ۳ نفره.
- «بام روی حاکم» هم تشخیص داده می‌شود.
- پیش‌فرض **روشن** است (مثل بازی واقعی) و از تنظیمات میز خاموش می‌شود.

### ۳.۲.۴ — کوت و حاکم‌کوت قابل تنظیم

- امکان خاموش کردن کوت (همه راندها ۱ امتیاز) برای بازی ساده‌تر.
- امکان تنظیم امتیاز کوت و حاکم‌کوت.

### ۳.۲.۵ — تاریخچه و لاگ اتفاقات بازی

الان فقط یک جمله `lastEvent` داریم که با هر حرکت جایگزین می‌شود.

- نگه‌داشتن فهرست رویدادهای راند (چه کسی چه کارتی زد، چه کسی دست را برد).
- نمایش «دست قبلی» تا بازیکن ببیند چه گذشت.
- سقف اندازه لاگ تا snapshot دیتابیس بی‌نهایت بزرگ نشود.

### ۳.۲.۴ و ۳.۲.۵ — حذف شدند

تنظیم امتیاز کوت و لاگ اتفاقات بازی، طبق تصمیم کاربر انجام نمی‌شوند.
دلیل حذف لاگ: بخشی از جذابیت حکم این است که بازیکن خودش حواسش باشد چه
کارت‌هایی بازی شده و بر اساس آن استراتژی بچیند.

### ۳.۲.۶ — ربات‌های هوشمند با سه سطح سختی ✅ انجام شد

ربات قبلی همیشه کم‌ارزش‌ترین کارت مجاز را بازی می‌کرد و **یار خودش را هم
می‌بُرد**. حالا ربات‌ها مثل یک انسان تصمیم می‌گیرند و سه سطح دارند.

| سطح | رفتار |
|---|---|
| **آسان** | اصول را بلد است (دست را می‌گیرد، یارش را نمی‌بُرد) ولی مثل یک بازیکن معمولی گاهی اشتباه می‌کند |
| **متوسط** | هیچ‌وقت اشتباه نمی‌کند؛ همیشه دست را ارزان می‌گیرد و از بلندترین خالش شروع می‌کند |
| **سخت** | تمام کارت‌ها را می‌شمارد؛ برنده‌های قطعی را نقد می‌کند؛ با حکم بلند، حکم حریف را می‌کشد؛ از خال کوتاهش خالی می‌شود؛ خالی که حریف در آن خالی است را بازی نمی‌کند |

**نکته مهم درباره «آسان»:** به‌جای بازی کاملاً تصادفی، حالا بیشتر مواقع درست
بازی می‌کند و فقط ۲۵٪ مواقع اشتباه می‌کند. این هم انسانی‌تر است و هم باعث می‌شود
مبتدی‌ها حس نکنند با یک ربات بی‌منطق بازی می‌کنند.

**تنظیم جداگانه برای هر ربات:** موقع اضافه کردن می‌توانی سطحش را انتخاب کنی و
بعداً هم از داخل لابی عوضش کنی. یک میز می‌تواند هم‌زمان ربات آسان و سخت داشته باشد.

**اندازه‌گیری واقعی قدرت:** به‌جای حدس زدن، هزار مسابقه بین سطوح شبیه‌سازی شد
(با جابه‌جایی صندلی‌ها تا مزیت صندلی اول خنثی شود):

- متوسط در برابر آسان: **۷۴٪** برد
- سخت در برابر آسان: **۷۶٪** برد
- سخت در برابر متوسط: **۵۵٪** برد

همچنین هر سه سطح در برابر **نسخه قبلی خودشان** آزمایش شدند و همگی قوی‌تر شدند:
آسان ۹۹٪، متوسط ۵۱٪ و سخت ۵۲٪.

⚠️ نکته مهم: نسخه اول «سخت» در واقع **ضعیف‌تر** از متوسط بود (۲۷٪) چون
تصمیم گرفته بود حکم‌های کوچک را ذخیره کند. با اندازه‌گیری مشخص شد این کار
بیشتر از فایده‌اش ضرر دارد و حذف شد. این تست به‌صورت خودکار در CI اجرا می‌شود
تا دوباره چنین چیزی رخ ندهد.

### قوانین اجرا

مثل مراحل قبل: هر زیرمرحله جداگانه پیاده‌سازی، تست و نقد می‌شود. هیچ قانون
اختیاری‌ای نباید رفتار پیش‌فرض فعلی را عوض کند مگر آنکه کاربر صریحاً روشنش کند،
و همه‌ی ۲۳۰ تست موجود باید سبز بمانند.

# فاز ۴ — UI/UX مدرن و جذاب

هدف: تبدیل «اپی که کار می‌کند» به «بازی‌ای که دلت می‌خواهد بازش کنی».

**تصمیم‌های بصری کاربر (قطعی):**
- تم **همیشه تیره**؛ هرگز روشن نشود، حتی اگر تلگرام روشن باشد.
- پالت **بنفش تیره** فعلی حفظ و صیقلی شود؛ هویت رنگی عوض نمی‌شود.
- بدون آیکن تاج برای میزبان (با «حاکم» اشتباه می‌شود).

## ۴.۱ — پایه: سیستم طراحی و رفع باگ فونت ✅

- فونت Vazirmatn **محلی** شود. الان از `fonts.googleapis.com` می‌آید که روی
  شبکه‌ی فیلترشده در دسترس نیست (تست شد: کد ۰۰۰) و متن فارسی با فونت
  پیش‌فرض سیستم رندر می‌شود. دقیقاً از همان خانواده‌ی باگ اسکریپت تلگرام.
- توکن‌های طراحی: رنگ، فاصله، شعاع گوشه، سایه، ترنزیشن، لایه‌بندی z-index.
- بازنویسی هفت فایل CSS روی توکن‌ها (الان `#00d4aa` و مشابهش ده‌ها بار
  تکرار شده‌اند).
- پشتیبانی از `safe-area-inset` برای آیفون‌های نوچ‌دار.

## ۴.۲ — میز بازی واقعی ✅

- چیدمان بازیکنان دور میز متناسب با ۲ / ۳ / ۴ نفره؛ خودت همیشه پایین.
- هر بازیکن: آواتار، نام، تعداد کارت، نشانگر نوبت، نشان حاکم، وضعیت اتصال.
- کارت بازی‌شده **جلوی صاحبش** بنشیند، نه در یک ردیف بی‌هویت.
- تیم‌بندی با رنگ مشخص شود (الان در میز اصلاً معلوم نیست یارت کیست).

## ۴.۳ — کارت‌ها و انیمیشن ✅

- بازطراحی کارت‌ها: تایپوگرافی، نماد خال، حالت‌های انتخاب و غیرمجاز.
- پخش کارت با تأخیر پلکانی، حرکت کارت به مرکز، جمع‌شدن دست به سمت برنده.
- همه پشت `prefers-reduced-motion`.

## ۴.۴ — انتخاب حکم به‌صورت Bottom Sheet ✅

- شیت از پایین با انیمیشن، چهار خال با هدف لمسی حداقل ۴۴×۴۴.
- تله‌ی فوکوس و کلید Escape، مثل کاری که برای `RulesGuide` انجام شد.

## ۴.۵ — ادغام با تلگرام

- Haptic: ضربه‌ی سبک روی بازی کارت، موفقیت روی بردن دست، خطا روی حرکت غیرمجاز.
- `viewportStableHeight` برای ارتفاع درست، `setHeaderColor` هماهنگ با تم تیره.
- همه با fallback امن: نبود SDK هرگز نباید باعث خطا شود.

## ۴.۶ — بازطراحی لابی و صفحه‌ی ورود

- صفحه‌ی ورود جذاب‌تر، کارت صندلی با آواتار، نمایش صریح تیم‌ها.
- انتخابگر حالت بازی بصری‌تر.

## ۴.۷ — صیقل نهایی و پوشش تست

- بستن شکاف پوشش: `TableScreen.tsx` (۴.۹٪) و `App.tsx` (۵۲٪).
- بازبینی کنتراست بر اساس WCAG AA و بررسی نهایی RTL.
