# معماری Hokm Club

این سند توضیح می‌دهد پروژه از چه لایه‌هایی ساخته شده، هر لایه مسئول چیست و
داده چطور بین آن‌ها جریان پیدا می‌کند.

> برای نصب و اجرا [`README.md`](../README.md) را ببینید.
> برای وضعیت فازها [`ROADMAP.md`](ROADMAP.md) را ببینید.

---

## اصول حاکم بر طراحی

۱. **موتور بازی از همه‌چیز مستقل است.** `@hokm/game-engine` هیچ ایده‌ای از
   تلگرام، HTTP، سوکت یا دیتابیس ندارد. ورودی می‌گیرد و state جدید برمی‌گرداند.
   به همین دلیل تست‌کردنش ارزان است و ۱۰۰ تست دارد.
۲. **سرور تنها مرجع حقیقت است.** کلاینت هیچ‌وقت قانونی را اجرا نمی‌کند؛
   فقط درخواست می‌فرستد و snapshot می‌گیرد.
۳. **هر بازیکن فقط دست خودش را می‌بیند.** این در `toPublicView` تضمین می‌شود.
۴. **یک نقطه برای پیکربندی.** فقط `config.ts` متغیرهای محیطی را می‌خواند.
۵. **فایل‌های کوچک.** هدف: هر فایل حدود ۲۵۰ خط یا کمتر.

## `@hokm/game-engine` — موتور قوانین

تابع‌های خالص روی یک state تغییرناپذیر. هیچ I/O، هیچ وابستگی خارجی.

| فایل | مسئولیت |
|---|---|
| `types.ts` | تایپ‌های مشترک: کارت، خال، بازیکن، وضعیت بازی |
| `cards.ts` | ساخت دسته، بر زدن با seed مشخص، مقایسه‌ی ارزش |
| `modes.ts` | `ModeConfig` برای هر سه حالت: تعداد صندلی، تیم‌بندی، الگوی پخش |
| `rules.ts` | شروع بازی، انتخاب حکم، جریان کلی یک دست |
| `legal-moves.ts` | اینکه چه کارتی مجاز است (رعایت خال زمینه) |
| `trick.ts` | تعیین برنده‌ی هر دست |
| `hand-flow.ts` | پایان دست، امتیازدهی، چرخش حاکم |
| `redeal.ts` | قانون ده‌لو کم |
| `duel.ts` | مکانیک سوزاندن و برداشتن در حالت دو نفره |
| `public-view.ts` | ساخت snapshot اختصاصی هر بازیکن |
| `internal/state.ts` | کمک‌تابع‌های داخلی state |

### مسیر یک دست بازی

```
شروع  →  تعیین حاکم  →  پخش ۵ کارت  →  [ده‌لو کم؟]  →  انتخاب حکم
      →  پخش بقیه‌ی کارت‌ها  →  حلقه‌ی دست‌ها  →  امتیازدهی  →  دست بعد
```

در حالت دو نفره بین «انتخاب حکم» و «حلقه‌ی دست‌ها»، دو فاز اضافه
`discarding` و `drawing` قرار می‌گیرد.

## `@hokm/api` — بک‌اند

### لایه‌ها

| مسیر | مسئولیت |
|---|---|
| `server.ts` | فقط composition root: ماژول‌ها را به هم وصل و سرور را روشن می‌کند |
| `config.ts` | تنها جایی که `process.env` خوانده و اعتبارسنجی می‌شود |
| `state.ts` | نگهداری میزها در حافظه به همراه بارگذاری اولیه از دیتابیس |
| `storage.ts` | پایداری SQLite با نوشتن اتمی (temp + rename) و بازیابی فایل خراب |
| `session.ts` / `auth.ts` | نشست بازیکن و بررسی توکن با زمان ثابت |
| `telegram-auth.ts` | اعتبارسنجی امضای HMAC روی `initData` |
| `schemas.ts` | اعتبارسنجی ورودی با zod |
| `errors.ts` / `messages.ts` | خطاها با کد انگلیسی و پیام فارسی |
| `rate-limit.ts` | محدودسازی نرخ با پنجره‌ی لغزان در حافظه |
| `sanitize.ts` | پاک‌سازی نام نمایشی |
| `room-lifecycle.ts` | وضعیت میز و سیاست انقضا |
| `http/` | اپ Express، میان‌افزارها، مسیرهای میز |
| `realtime/` | هندلرهای Socket.IO و پخش snapshot |
| `game/` | سرویس میز، ربات‌ها و هوش مصنوعی آن‌ها، ساخت view |
| `telegram/` | ربات grammY و پروکسی اختصاصی آن |
| `jobs/` | پاک‌سازی دوره‌ای میزهای رهاشده |

### احراز هویت

```
initData از تلگرام
        │
        ▼
secret_key = HMAC_SHA256("WebAppData", bot_token)
        │
        ▼
بررسی امضا + انقضای ۲۴ ساعته‌ی auth_date
        │
        ├─ معتبر   → هویت واقعی تلگرام، امکان پس‌گرفتن صندلی
        └─ نامعتبر → رد، مگر ALLOW_UNVERIFIED_TELEGRAM=true (فقط توسعه)
```

`telegramId` ارسالی از سمت کلاینت **هرگز** پذیرفته نمی‌شود.

### ربات‌ها

`bot-ai.ts` منطق اصلی، `bot-memory.ts` شمارش کارت برای سطح سخت،
`bot-duel.ts` تصمیم‌های مخصوص حالت دو نفره.
سطح آسان همان منطق درست را دارد ولی با نرخ خطای مشخص اشتباه می‌کند.

## `@hokm/web` — مینی‌اپ

| مسیر | مسئولیت |
|---|---|
| `main.tsx` | نقطه‌ی ورود؛ ابتدا SDK تلگرام را با مهلت بارگذاری می‌کند |
| `App.tsx` | چیدمان صفحه‌ها و اتصال هوک‌ها به هم |
| `api/client.ts` | درخواست‌های HTTP؛ هر خطا به پیام فارسی تبدیل می‌شود |
| `api/socket.ts` | اتصال Socket.IO با تنظیمات اتصال مجدد |
| `api/session-storage.ts` | ذخیره‌ی نشست و آدرس API |
| `api/telegram-sdk.ts` | بارگذاری امن SDK با مهلت، تا CDN مسدود صفحه را قفل نکند |
| `hooks/useSession.ts` | مالکیت نشست بازیکن و چرخه‌ی `idle`/`resuming`/`active` |
| `hooks/useRoomConnection.ts` | پیوستن به میز، دریافت بروزرسانی‌ها، مدیریت قطعی |
| `hooks/useGameActions.ts` | اکشن‌های حین بازی |
| `hooks/useLobbyActions.ts` | اکشن‌های لابی |
| `components/` | ۱۴ کامپوننت رابط کاربری |
| `styles/` | CSS تفکیک‌شده بر اساس ناحیه |

### اتصال مجدد

در **هر** رویداد `connect` دوباره `room:join` فرستاده می‌شود — نه فقط بار اول.
عقب‌نشینی نمایی بین ۰.۵ تا ۵ ثانیه با jitter انجام می‌شود تا وقتی سرور برمی‌گردد
همه‌ی کلاینت‌ها همزمان هجوم نیاورند. باز بودن چند تب هم مدیریت شده است.

## جریان داده در یک حرکت

```
۱. بازیکن روی کارت می‌زند
۲. مینی‌اپ رویداد game:play_card را با نشست خود می‌فرستد
۳. سرور نشست را با زمان ثابت بررسی می‌کند
۴. سرور ورودی را با zod اعتبارسنجی می‌کند
۵. موتور بازی مجازبودن حرکت را تعیین می‌کند
۶. state جدید ساخته می‌شود
۷. اگر نوبت ربات شد، ربات‌ها حرکت می‌کنند
۸. state روی دیتابیس ذخیره می‌شود (اتمی)
۹. برای هر بازیکن یک snapshot اختصاصی ساخته و ارسال می‌شود
```

مرحله‌ی ۹ حیاتی است: `toPublicView` دست بقیه‌ی بازیکنان و پاکت را حذف می‌کند.
یک بار این‌جا باگ داشت و کل state با spread فرستاده می‌شد که بازی را قابل تقلب
می‌کرد؛ الان تست اختصاصی نگهبانش است.

## تصمیم‌های مهم و دلیلشان

| تصمیم | دلیل |
|---|---|
| `sql.js` به‌جای دیتابیس واقعی | بدون نیاز به بیلد native، روی ویندوز و لینوکس یکسان اجرا می‌شود |
| نوشتن اتمی با temp+rename | قطع برق وسط نوشتن، فایل را خراب نمی‌کند |
| ربات‌ها همیشه آماده هستند | با این کار میز با ۱ تا ۴ انسان کار می‌کند |
| بدون جست‌وجوی درختی در ربات سخت | برای یک Mini App سنگین است؛ محدودیت آگاهانه پذیرفته شد |
| بارگذاری SDK تلگرام با مهلت | CDN مسدود نباید کل برنامه را قفل کند |
| پروکسی جدا فقط برای Bot API | VPN سیستمی تونل را می‌شکند |
